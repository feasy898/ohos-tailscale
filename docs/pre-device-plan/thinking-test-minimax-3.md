## 1. 测试对象分析：我怎么给 25 个工作项分类

PLAN §2 有 P0-1…P0-8（8 项）+ P1-1…P1-14（14 项）+ P2-1…P2-3（3 项）。我按**「产出物的可判定性」**分三类，而不是按 PLAN 的章节分——因为测试的组织方式应该跟着判定方式走。

### 1.1 甲类：产出物是**可执行代码/门**，判定在 host 机（本机 exit code 即裁决）

P0-1（peerapi-tun 修型）、P0-2（stun Generator 展开）、P0-3（validate:arkts 门）、P0-4（gate-d4 脚本）、P0-5（regress 改造 + selftest）、P0-7（.gitignore）、P0-8（arkts-check.js）、P1-1（kat 包）、P1-4（vpn-config）、P1-5（platform-ports）、P1-7（integration-mirror）、P1-8（interop tsc）、P1-10（upstream-lineref）、P1-11（evidence 校验器）、P1-13（perf 源码）、P1-14（gates 聚合）、P2-1（upload 真 HTTP）。

判据形态固定为**「红→绿轨迹 + 负对照」**：每个门必须能证明自己会红。PLAN 自己在 P0-3/P0-4/P0-5/P0-5-seltest 里都写了「负对照/注入违规样本→exit 非 0」，这是本仓已有的好纪律（BASELINE §2.9(a) 亲自把 CI 脚本喂 bash 复现 exit 2 就是同一手法），我要做的是把它**从 4 项推广到全部甲类门**。

### 1.2 乙类：产出物是**文档/口径/剧本**，判定是「文本断言」——这是我的主轴

P0-6（交接包 + check-stage-docs.mjs）、P1-2（口径清零）、P1-3（文档门阻断）、P1-6（CU 卡）、P1-12（OWNER-GUIDE + env-ready schema）、P2-2（快照去重）、P2-3（FACTS-APP）。

这一类的危险与甲类**正交**：甲类测试抓「代码没改对」，乙类测试抓「代码改对了但文档在骗人」。BASELINE §1 最后一行「读文档会得出错误结论」说的就是乙类；§6 勘误表 8 条 + 2 条工具头注释 + yml 注释，全部是乙类的靶子。

我把乙类再切一刀：
- **乙-口径**（P1-2 / P1-3 / 部分 P0-6）：数字一致，详见 §3。
- **乙-交接**（P0-6 / P1-6 / P1-12）：文档里每条命令/每个判据是否真实存在、是否可判定，详见 §4。
- **乙-存在性**（A15）：七份文件在不在盘——最朴素但最容易漏，因为 PLAN 自己在 §1.1 A15 里才发现「不存在」。

### 1.3 丙类：**只能真机/人类判定**，本机只能测「它变成了可判定的形态」

B1–B8 全部，以及 S0–S8 剧本本体。我的立场很硬：**丙类的答案不进 A 类完成定义**（PLAN §1.2 已明文，我完全同意）。但丙类里有一层是甲/乙类能测的——**「探针自洽性」**：CU 卡有没有二值判定、两分支预案有没有空占位；STAGE-CHECKLIST 的命令标签全集与剧本引用命令全集差集是否为空；env-ready.schema.json 能不能被校验器加载并拒绝坏样本。这些是 PLAN A11/A15 的字面要求，我把它们当作**丙类的准入测试**而不是丙类本身。

**这条线怎么划的**：判据是「裁决所需的输入是否在本机可得」。`hdc list targets` 需真机 → 丙类；但「文档里是否写了 `hdc list targets` 这条命令、且标了 `[device]` 标签」只需读文本 → 乙类。同一条命令在两个测试里出现是正常的，不是重复。

## 2. 可见测试 vs holdout 测试：划分原则

### 2.1 我的原则（三条，按优先级）

**原则一：规格可见，答案不可见。**
开发 agent 必须能看到「测什么」——否则它无法知道 P0-1 修 TS2353 的正确形态是「传真函数 + 正控制组」还是「删断言」。PLAN A1–A16 就是现成的规格表，直接作为可见测试的**断言清单来源**。但**期望值必须由测试在运行时从真值推导**，不能由 agent 预写进文档。

**原则二：holdout 存「反例库」与「变异检测器」，不存「答案」。**
这是我对 holdout 的核心设计判断。常见做法是把整份测试藏起来，我否决——见 §6.2。

**原则三：凡「改代码不改文档必须红」的测试，可见；凡「文档里写什么」的自由度，holdout 看不见也不必看见。**
P1-2 清零后，谁写「495 pass / 0 fail」还是「495/0 全绿」还是「≥495/0」都不影响正确性——文风自由度不该被 holdout 锁死，否则 agent 会为了迎合正则去改文风，反而制造噪音。

### 2.2 具体划分表

| 测试族 | 可见 | holdout | 理由 |
|---|---|---|---|
| 甲类各门的「exit 0 + 负对照红」 | ✅ | — | 规格就是 PLAN 验收条目，藏了 agent 做不了 |
| A1/A2 的**下限断言**（tests ≥495） | ✅ | — | PLAN §1.1 明文 |
| **精确数字推导器**（跑真门 → 取出真实值 → 与文档比对） | — | ✅ | 推导逻辑藏起来，agent 就不能「把门改成输出期望值」 |
| **旧数字残留黑名单的真实条目** | ✅（示例 3 条） | ✅（完整表） | 3 条已公开的（280/六包/238）足以传达意图；完整表防「只清了我看见的那几处」 |
| **假命令检测器**（hvigorw 类） | ✅ 规则可见 | ✅ 语料 | 规则公开（否则无法自证），但注入的坏语料不能提前给 |
| STAGE-CHECKLIST 标签差集检查 | ✅ | — | 交接包自身就是规格 |
| env-ready schema 校验 | ✅ 规则可见 | ✅ 坏样本集 | 同上 |
| CU 卡二值判定/分支完整性 | ✅ | — | 规则简单，防的就是「写个占位符」 |
| **口径漂移的「变异检测」自测** | — | ✅ | 见 §2.3 |
| S0–S8 的本机可测前置（S1 剧本自检） | ✅ | — | PLAN A11 已把它定为 A 类 |
| S3–S8 真机判定本身 | ❌ 不测 | ❌ | 本机结构性不可达（PLAN §0） |

### 2.3 一条我特意加的 holdout：**测试自身的变异检测**

这是我认为防过拟合最有效的一招，也是 holdout 最该装的东西。对甲类门与乙类门各做一批**人工/半自动变异**：把 `makePeerServer` 改回坏形态、把 stale 数字塞回 README、把 env-ready 的某个字段删掉、把 CU 卡的分支改成「待定」——然后断言**对应的测试必须变红**。红不了的测试是死测试。

这个测试我**不会**放进可见集，因为它等于把变异清单交给 agent。我自己在写正式测试时可以先手工跑几例验证检测器有效，但那份清单入 holdout。

## 3. 乙-口径测试：单一事实源与旧数字残留

这是我的主轴核心，也是 PLAN A16 与 P1-3 的靶心。PLAN A16 写的是「旧数字否定断言（280/13/54/238/「六包」等 0 命中于活文档面）」。**我实测认为这个设计照抄会立刻变成噪音门**，理由在 §3.3。

### 3.1 单一事实源放哪：四个候选与取舍

先说约束事实：`node_modules` 只有 5 个包（E17），**无 ajv、无 yaml**；禁 `npm install`。所以事实源必须零依赖——这直接排除了很多花活。

| 方案 | 形态 | 优点 | 我否决/采纳的理由 |
|---|---|---|---|
| **S1 写死在校验脚本里** | `scripts/doc-consistency.mjs` 内 `const TESTS_MIN=495` | 零新增文件 | ❌ 否决：这只是把「手抄数字」从文档搬到脚本，抄错了照样红/绿，而且要改两处（脚本+文档）。**这是把原问题平移** |
| **S2 package.json 字段** | 加 `"gates": {"tests": 495, ...}` | 单一文件、天然入仓、npm 生态熟悉 | ⚠️ 次选：`package.json` 已被 4 个工作项改（脚本新增），并发改同一文件易冲突；且「文档里写的数」本质是**多值**（≥495 还是 =495），塞进一个标量字段语义不干净 |
| **S3 专门 JSON（无值，只有结构）** | `docs/pre-device/caliber.json` 声明**每个数字的取法**（跑什么命令、正则怎么提、下限还是精确），**不写死数值** | 值永远来自真跑，无人可抄错；「≥495」这类语义可表达；agent 无法通过改数值造假 | ✅ **采纳**。这是「校验式」路线 |
| **S4 生成式** | 从真值**生成**文档片段（README 的 G0 表由脚本注入） | 天然不可能漂移 | ❌ 否决（本轮）：会大改 README/CONTEXT 结构，撞「禁止修改过多既有文件」的红线气质，且 Markdown 生成器在无依赖约束下易写出难读的产物；S3 已经能捕获漂移，生成式的收益（结构统一）不值这个代价。**留作二期备选** |

**我的结论：S3「无值结构 + 运行时真值」的校验式路线。** 落点是 `docs/pre-device/caliber.json`（PLAN A15 已要求该目录存在，正好搭车），配 `scripts/doc-consistency.mjs` 消费它。

`caliber.json` 的每个条目我设计成四元组：`{ id, cmd, extract, relation: "min"|"eq", surfaces: [...] }`。例：

```json
{ "id": "tests",     "cmd": "npm test",            "extract": "^# tests (\\d+)", "relation": "min" },
{ "id": "bridge",   "cmd": "npm run test:bridge",  "extract": "^# tests (\\d+)", "relation": "min" },
{ "id": "shell",    "cmd": "npm run validate:shell","extract": "summary: (\\d+) passed", "relation": "min" }
```

`relation: min` 对应 PLAN A1 的「≥495（数字只增不减）」语义——这点很重要：**用 `min` 而不是 `eq`，A 类门自然不会被新增用例卡红**（P1-1 kat、P1-4 vpn-config 都会加例数）。这是我实测 E2/E3 后定的口径。

### 3.2 文档侧怎么比对：不是「含 495」，是「所有声称测试数的数字必须 ∈ {实测, 已知历史集}」

CI 现状是 `grep -q "$T_TOTAL" "$f"`——只查「含不含」，且 E8 证明它空值时恒真。升级后的断言要分**肯定**与**否定**两侧：

- **肯定侧**：文档中出现的「测试/用例数」必须等于实测值或历史值集合。我实测活跃文档面里 495 出现 11 次、66 出现 9 次、30 出现 7 次、29 出现 25 次——**同一份仓库里同时存在 29 与 30 两个「当前值」**，这正是要抓的。
- **否定侧**：见下。

### 3.3 旧数字黑名单：实测假阳性率 **46%**，必须重新划边界

我把 PLAN A16 的黑名单原样跑了一遍（E9），得到 **28 处命中**。逐条分类：

| 命中位置 | 性质 | 判 |
|---|---|---|
| `README.md:10`（8400 行）、`:12`（54 用例）、`:42/:44/:45`（280/13/54 第二张表） | 真陈旧 | ✅ 该红 |
| `TASK.md:18`（≥280）、`:20`（≥13）、`:21`（≥54）、`:60`（≥54）、`:67`（280/13 用例） | 真陈旧 | ✅ 该红 |
| `HARMONY_AGENT_TASK.md:9/:49/:82/:88` | 真陈旧 | ✅ 该红 |
| `DELIVERY_REPORT.md:60`（1066 行） | 真陈旧 | ✅ 该红 |
| `CONTEXT.md:15` 的「217→238→495」 | **合法时序叙事** | ❌ 误伤 |
| `TASK.md:28`「修正 CONTEXT 的『6 包』『238 pass』」 | **自指**：这条待办本身在**引用**待修的词 | ❌ 误伤 |
| `DELIVERY_REPORT.md:14/:16/:77/:105/:119/:120/:208/:221/:223/:224/:231` | **历史交付记录 / 前后对比表** | ❌ 误伤 |

**15 真 / 13 假 = 46% 假阳性。** 而且误伤形态很恶劣：`DELIVERY_REPORT.md:224` 那行「54 / 0 failed → 66 / 0 failed（+12）」是 BASELINE 认定的**正面历史记录**，黑名单会逼 agent 去删历史证据——这与 PLAN §3.3「证据不被吞」的精神直接冲突。

**我的边界设计（三条叠加，缺一不可）：**

1. **按「断言语境」而非「出现」判**。黑名单词只有出现在**声称当前状态的句子里**才红。判据形态：命中行需同时含**当前态标记**（`当前`/`现行`/`现状`/`≥`/`期望`/`pass`/`passed`/`全绿`/表格首列口径位）之一，且**不含**历史标记（`基线`/`初版`/`更新轮`/`09-29`/`历史`/`上一轮`/`+257` 这类增量标记）。
   - 反例检验：`DELIVERY_REPORT.md:224` 行内含 `54 / 0 failed` 与 `66` 与 `+12` → 含增量标记 → 豁免 ✅
   - `README.md:45` 含 `54 passed / 0 failed` 无增量标记 → 命中 → 红 ✅
2. **显式豁免表**（放在 `caliber.json` 里，人可审、可改）：`TASK.md:28` 这种**自指待办**必须登记豁免，否则 P1-2 会陷入「改了待办就又命中」的活锁。我要求豁免项必须写 `reason`，且豁免清单本身进 holdout 复核（防 agent 随手加豁免行）。
3. **黑名单词要带语义形状，不能只带裸数字**。PLAN 写的 `13` 我实测命中 4 处，其中 `TASK.md:20`（≥13）与 `README.md:44`（13 pass）是真陈旧，但 `\b13\b` 太宽；改成 `(?:≥\s*13|13\s*(?:pass|passed|用例|个用例))` 这类**上下文正则**精确度显著更高。同理 `六包` 我实测命中 10 处，其中 6 处在 DELIVERY_REPORT 历史段——加历史标记豁免后只剩 4 处真命中。

### 3.4 「改代码不改文档必须红」的连锁更新检测

这是 R7（PLAN §6）要求的。设计如下：

**断言形式**：对每个 `relation:"eq"` 的口径数字（当前只有规模类：72 文件/16904 行/8 包——测试数走 `min` 不参与），**扫全活文档面**，出现次数必须 ≥1 且每个出现的值都等于真值。我实测 E3 得到 72/16904/49/13170 是**可机检真值**（`find`+`wc` 零依赖可复跑），所以规模类可以做 `eq` 强断言。

**检测能力自证（必须做）**：写一个**变异脚本** `scripts/mutate-doc-number.mjs`，把 README 的 16904 改成 16903、跑门、断言 exit≠0、然后还原。**没有这一步，这个测试就是假绿的**——我见过太多「断言写了但从不变红」的测试。

**关于 P0-1 的连锁**：E9 显示 bridge=30 在活跃文档面出现 7 次（README:24/:37、docs/handover/README.md:17、owner-with-real-device.md:27 等）。P0-1 加 1 例 → 31，P1-4 后 ≥36。按我 §3.1 的 `min` 口径，**这些点不会红**（30 ≤ 实测），这正是我要的：数字只增不减是纪律，不是每次都要全文同步。但 P1-2 又要求把「30」写成现行口径——**这两条会打架**。

**我的裁决建议**：`caliber.json` 里每个口径额外带 `floor`（历史值，只增不减不红）与 `current`（现行值，必须一致）两个概念，`relation:"eq"` 只对 `current`。P1-2 完成后 `current=31`，门会比对「文档里声称的现行值 == 31」；在此之前 `current=30`。这需要合并人裁决（§7）。

## 4. 乙-交接测试：假命令检测与 S0–S8 可测化

### 4.1 假命令检测器：三类「假」，得分开测

hvigorw 教训（BASELINE §8 缺陷 4 + PLAN P0-6）只覆盖了第一类。我实测发现交接文档里至少还有两类：

| 类 | 定义 | 实测证据 | 检测法 |
|---|---|---|---|
| **F1 命令不存在** | 二进制在本机/在仓内都不存在 | E6：`hvigorw` NOT FOUND，且 `find . -name 'hvigorw*'` 空 | 白名单化：`hdc/hvigorw/deveco/sdkmgr/ohpm/docker/headscale` 是**合法**的设备侧命令，不该报红；判据是「该命令在**其归属环境**是否存在」——hvigorw 错在 `docs/handover/`（owner 有 DevEco 的场景）被写成了裸命令行 |
| **F2 环境变量/参数是编的** | 文档给的 env/flag 在代码里没人读 | E14/E15：PLAN P0-5 要让 regress 读 `HS_PREAUTHKEY`，但**当前代码只有 `HS`**。若有人在 P0-5 之前就改文档写 `HS_PREAUTHKEY=… npm run interop:regress`，那就是 F2 | **env-var 交叉引用检查**：抽出文档里 `VAR=value cmd` 形态，`grep -rn "process.env.VAR"` 断言 ≥1 命中。这是零依赖可做的 |
| **F3 路径不存在** | 命令引用的仓内路径不在盘 | E19：`app/entry/build/default/outputs/default/entry-default-signed.hap` MISSING——**但这条是真陈旧**（壳从未编译，产物路径本就编造） | 仓内路径 `test -e`；但要豁免「构建产物」类（`build/`、`*.hap`、`*.abc`），否则 P0-3 的镜像产物目录也会误伤 |

补充一类我发现的：**F4 npm script 不存在**。E6 里我核对了交接文档引用的 `npm run test:bridge/typecheck/validate:shell` 全部存在于 package.json——**当前是干净的**。但 P0/P1 会新增 `validate:arkts`/`gate:d4`/`test:kat`/`gates`，一旦文档先写脚本后建脚本就中招。检测：`npm run <name> --dry-run` 不可靠（实测 `npm run definitely-not -a-script` 退出码竟为 0！见 E11 邻项），所以应读 `package.json.scripts` 键集做集合差——**这条我实测踩过坑，`npm run` 的退出码不能用来判存在性**。

### 4.2 STAGE-CHECKLIST 的「标签差集为空」：这条断言其实有个洞

PLAN A11 写「命令标签差集为空」。我理解为：STAGE-CHECKLIST 里每条命令标了 `[local]`/`[device]`/`[human]`，且**剧本（AGENT-TASK/OWNER-GUIDE）引用的命令集合 == CHECKLIST 标注的命令集合**。

**我认为这个差集是双向的，单向会漏**：
- `CHECKLIST \ 剧本` 非空 = 清单里有命令但剧本没引用（冗余，低危）
- `剧本 \ CHECKLIST` 非空 = **剧本让人跑了某条命令，但清单没标它**——**这是高危**：R1（PLAN §6）说的正是「真机 agent 误诊环境/人工确认点为代码问题」，而一条没进清单的命令正是漏掉的环境前置。

所以测试应断言**两个差集都空**，且第二个差集为空时给更重的失败文案。我建议这条进 holdout（剧本与清单的**配对**是 PLAN 没写的隐含契约，公开了 agent 可能只凑数量不管语义）。

### 4.3 env-ready.json：从「人类填过」到「可判定 IO」

PLAN S4：「人类填写 env-ready.json 全绿后才进 S5（把『是否问过人』变成可判定 IO）」。这是把人类步骤机检化的核心设计，我给它三层：

**L1 结构层**：schema 是 JSON（PLAN 已定），E17 证明无 ajv，所以**校验器必须手写**——我建议不写通用 JSON-Schema 子集引擎，只写针对该 schema 的定向断言函数（零依赖、可读、失败信息可写成人话）。这点 PLAN 没提，是个实现约束。

**L2 内容层（这是「全绿」的真正含义）**。PLAN §1.2 B 类列了六项：SN 可见、签名方式已选、VPN 授权预期、headscale LAN 地址、preauthkey 已备、第二 peer 已定。我建议每项不只是一个 bool，而是**「值 + 证据」二元组**：

```json
{ "sn": { "value": "ABC123", "evidence": "hdc list targets 输出行", "confirmed_by": "owner", "at": "2026-10-03T14:00+08:00" } }
```

理由：PLAN §3.4 回报格式明写「贴原始输出而非结论（防绿灯幻觉）」。如果 env-ready 只是 bool，它就是**唯一一个允许人只填结论不留证据的门**，与全篇精神相反。L2 断言：每项必须有非空 `evidence` 字符串 + `at` 时间戳。

**L3 门控层**：S4→S5 的推进判据是「env-ready 全绿」。这条本身无法在本机测（真机流程），但**「门控逻辑」可以测**：写一个 `assertEnvReady(obj)` 纯函数，喂 6 个缺字段/空 evidence/错误类型的样本，断言全红。这正是 §2.2 里说的 holdout 坏样本集。

**边界诚实声明**：env-ready.json 只能证明「人声称确认过」，**不能证明环境真的就绪**。L3 测试能防「漏填」，防不了「填假」。PLAN R1 的残余风险因此仍在——我不假装这个 schema 能关掉 R1。

### 4.4 OWNER-GUIDE 的三栏非空：从「非空」到「有信息量」

PLAN A15：「OWNER-GUIDE 每阶段『人提供/人决定/通过判据』三栏无空」。我实测认同「无空」是必要断言，但**它极易被凑数满足**（每格填「见上」「同上」「—」即过）。

我的加强设计：三栏各要求一个**可机检的最小形状**——
- 「人提供」栏须含一个**可执行产物名**（如 `app.json5`、`p12`、headscale 地址），用白名单/正则判存在性或格式；
- 「人决定」栏须含一个**决策标记**（选项字面量，如 `自动签名|p12|未签名`），命中其一即可；
- 「通过判据」栏须含一条**可判定输出串**（如 `INTEROP PASS`、`.hap`、`MapResponse`），且这些串**必须与 regress.mjs / AGENT-TASK 里实际打印的 marker 一致**。

最后这条交叉引用是关键：PLAN P0-5 正在把 marker 字符串重定义（`INTEROP PASS`/`DERP INTEROP PASS`/`H2C PASS`）。如果 OWNER-GUIDE 的判据栏写着旧 marker，**S6/S7 的「通过」就会是人眼认定而非机器认定**。marker 一致性检查应做成一个独立断言，且因为 P0-5 会改 marker，它必须在 P0-5 之后、P1-12 之前跑一次校准。

## 5. 机检集成：位置与命名

**npm scripts**（新增，全部挂在 PLAN 已有的 A6/A7/A8/A11/A16 上）：

| script | 归属工作项 | 内容 |
|---|---|---|
| `validate:docs` | P1-3 | 消费 `caliber.json`，跑 §3.2 肯定侧 + §3.3 否定侧 + 假命令 F1/F2/F3/F4 |
| `validate:stage` | P0-6 | `check-stage-docs.mjs`：双向差集 + CU 卡二值/分支 + OWNER-GUIDE 三栏 |
| `validate:handoff` | P0-6 | 假命令 F1–F4（与 validate:docs 分开，因为 grep 面不同、失败文案不同） |

**为什么不并成一个门**：P1-3 明确「必须在 P1-2 之后启用阻断」（R12/附录 B-8：先立门后清 → 全仓爆红 → 门被禁用）。拆成两个独立 script 就是**拆分生效点**——`validate:docs` 可先只跑肯定侧（不阻断），清零完成后再打开否定侧阻断。

**CI 位置**：PLAN P0-4 已定「yml 内不再有裸内联 grep，人工复核路径与 CI 路径必须同工具」。同理，`docs-consistency` job 应改为 `run: npm run validate:docs`，yml 里不再写 awk/grep 行。我实测 E7/E8 证明现状是**假绿**（T_TOTAL 空 → `grep -q ""` 恒真 → step exit 0），所以这不是「能力增强」而是**从假绿转真判**。

**新门命名**：沿用 `validate:*` 前缀（已有 validate:shell）。不用 `lint:docs`——本仓没有 eslint 生态，`lint` 会误导。

**必须进 `npm run gates`（P1-14）的只有 `validate:docs` 与 `validate:stage`**；`validate:handoff` 我建议**不进聚合门**，因为它在 P0 完成后会长期稳定，而它依赖的 marker/路径可能随 P0-5 演进，频繁红会养成「忽略」习惯。这条是取舍，理由记录在此。

## 6. holdout 的存放与保密机制

### 6.1 存放位置（三方案，取舍）

| 方案 | 形态 | 评价 |
|---|---|---|
| **H1 仓内独立分支** | `git branch holdout-tests`，开发 agent 在 `main` 上工作 | ⚠️ 有 git 的 agent `git branch -a` 就能看到（我实测当前只有 main，加入后必然可见）。**仅防「无意中读到」，不防「主动找」** |
| **H2 仓外目录 + 路径注入** | 放在 `D:/new-workspace/_holdout/`，跑测试时用 `HOLDOUT_DIR` 环境变量指入 | ✅ **采纳为主**。物理隔离，`ls` 不到 |
| **H3 加密归档** | 仓内放密文，运行时用口令解 | ❌ 否决：口令传递本身就是泄露面；且本仓 node 只有 5 个依赖，做加密要自己实现，引入不必要的复杂度 |

**采纳 H2 + H1 兜底**：H1 放一份「哪些能力有 holdout」的**索引**（不含内容），让验收流程可自证完整性；内容在 H2。

### 6.2 holdout 里装什么、不装什么（我的核心主张）

**不装**：整份测试。原因——PLAN 的 25 个工作项里大量是「实现一个新脚本/新文档」，规格全在 PLAN §2 各条的「文件/验收/依赖」字段。藏起来等于让开发 agent 猜验收标准，产出必然跑偏；而且**藏规格会诱发 agent 去读 PLAN 里 A1–A16 反推**，等于没藏。

**装**（四类，全部是「规格之外的判别力」）：
1. **变异集**：§2.3 说的变异清单——用来证明可见测试真的会红。
2. **黑名单完整表 + 豁免表**：可见集只给 3 条示例。
3. **坏样本集**：env-ready 的 6 个坏样本、CU 卡的无分支/单分支/空占位样本、STAGE-CHECKLIST 差集非空样本。
4. **推导器实现**：口径数字的提取逻辑（跑什么命令、正则、min/eq 语义）。这是「防 agent 把门改成输出期望值」的唯一手段。

### 6.3 保密怎么「落实」

我必须诚实：**在同一个 agent 能执行 shell 的环境里，没有任何软件手段能保证开发 agent 不读 holdout**。H2 只是提高读取成本，不是封锁。所以我的设计重心是**「即使读到了也无法通过」**：

- **推导器藏起来没有用**——agent 若读到 `caliber.json`，照样能改文档迎合。真正的防线是 §2.3 的变异检测：**agent 迎合文档之后，可见测试会不会红？** 会。因为变异集验证的是「文档偏离真值 → 红」，而真值来自跑真门，agent 改不了门（改了门 A1/A2 就红）。**真值链的锚是「跑真命令」，不是「脚本里的常量」**——这是我全部设计的支点。
- holdout 的真实价值是**验收时的独立裁决**：由不参与实现的第三方（合并人/owner）跑，能回答「这批测试本身有没有鉴别力」，而不是「agent 有没有作弊」。我不夸大它的作用。

### 6.4 谁跑、何时跑、判定标准（必答第 5 条）

| 阶段 | 跑什么 | 由谁 | 判定 |
|---|---|---|---|
| 开发中（每个工作项收口） | 可见集 + 对应工作项的负对照 | 开发 agent 自跑 | exit 0；**且必须留下红→绿轨迹**（PLAN P0-5 已明列为交付物，我主张推广到所有新门） |
| 批次收口（PLAN §2.5 四批次） | `npm run gates`（P1-14 落地后） | 开发 agent | 全绿 |
| **独立验收** | 可见集 **+ 完整 holdout** | **合并人/owner，不通知开发 agent 结果** | 全绿 **且** 变异集全部被检出 |
| 交接真机前 | A1–A16 全绿 + O1–O7 已递交 | owner | PLAN 文末定义 |

**失败怎么处置**——我主张分三级，因为一刀切会让 agent 改测试凑绿：
1. **可见集红**：正常修实现。
2. **holdout 红**：先怀疑测试。若确认测试错 → 改 holdout 并**记录理由**；若确认实现错 → 修实现。
3. **变异检测失败**（某个变异没被检出）：**这是测试体系的失败，不是实现的失败**，必须补测试，不能靠改实现让它「本来就红/本来就绿」。

**特别的红线**：为了让门变绿而修改**门自身**（放宽正则、删断言、把 `relation` 从 `eq` 改成 `min`）——这在 holdout 下可被检出（因为推导器在 holdout 里），我把它列为**作废本批证据**级违规，与 PLAN §3.4 对「改脚本/代码凑 PASS」的处理对齐。

## 8. 我认为最容易被漏掉的两项

1. **「测试自己会不会红」的变异检测**。本仓已有的好纪律（负对照/红→绿轨迹）目前只出现在 PLAN 的 4 个 P0 门里；推广到**全部**甲类门与乙类门，是防「假绿」唯一有效的手段。没有它，一个 `exit 0;` 空脚本也能满足 A6/A7/A8/A11 的字面验收。
2. **口径扫描范围与「实际会被维护的文档」之间的缺口**。实测发现 app/README-app.md、app/bridge/README.md 有陈旧数字但不在活文档面；docs/research/ 被当活文档用却归历史档案面。**门禁扫错范围 = 门禁给虚假安全感**，这比没有门更危险。我把「扫描范围本身」也做成一条可测断言：范围列表进 `caliber.json`，任何新增的顶层 README 都要显式归类（活/历史），未归类即红。
