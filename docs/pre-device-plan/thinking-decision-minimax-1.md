## 2. 逐项思考

### O2 regress 阶段 3：履约 vs 改约（我的主战场）

- **选项**：A 补 CLI（履 D-1）；B 删阶段 3（改 D-1）；C 保留阶段但降级为「非阻断告警」（第三种：既不改约也不履约，但把 false 变成 warn）；D 不动（维持现状）。
- **证据**：D-1 原文 `TASK.md:54`：「用隔离 headscale 实例…跑 `interop/start-headscale.sh` + register/h2c/derp：全部 exit 0 且输出含 `INTEROP PASS` 与 `DERP INTEROP PASS`」。注意 **D-1 只写了两条 PASS 串，没有第三条 h2c marker**——即 D-1 的「h2c」是**义务项**（要有 exit 0 的 h2c）而非独立标记项。`interop/regress.mjs:57-59` 调 h2c 但 `h2c.node.ts` 仅 `:29` 一个 `export class`、全文 281 行、`process.argv` 0 命中（亲验）→ 现状 exit 0 + stdout 空，被 `regress.mjs:42` 的 `stdout.length>0` 判负。BASELINE §8 缺陷 2 结论：**任何 headscale 环境下都不可能输出 INTEROP PASS**。
- **倾向 A（补 CLI）**。推理链：①`TASK.md:12` 把 §2 定为「验收标准（可判定；**数字即契约，改动须留痕**）」，`:88` 红线写「D4/P4/ArkTS 禁则不可放宽（放宽 = 改契约 + 留痕）」——**契约的修改权在契约主人（owner），不在执行者**；②A 与 B 的差别不是「哪个更省事」，而是「谁有权动 D-1」；③A 的成本极低：`register.node.ts:43-45` / `derp.node.ts:37-39` 已有 CLI 样板（`process.argv` 解构 + `usage:` 退出），照抄一段入口即可，属 S 级（PLAN P0-5 规模 M 中的子项）；④B 若执行，等于用「脚本形态」反推「契约该是什么样」，这是**用实现改约**——恰是本仓三次假绿事故的同构（TESTS §6「门存在但不跑 / 门在跑但没约束力 / 文档漂移」）。
- **反方最强论证**：`H2OverNoise` 已被两阶段真实调用——`register.node.ts:228` 实例化后 `:237` `h2.post(authority,'/machine/register',…)`、`:249` 附近再 post `/machine/map`；`derp.node.ts:200` 实例化后同样 post register。也就是说「h2 链路」在阶段 1、2 里**每次真跑都被走到**；独立阶段 3 的边际覆盖≈0，只是把同一次调用再跑一遍换取一个 marker。轨迹 3 的「阶段冗余」立场在覆盖率维度上是成立的，且它还省掉一次 Noise 握手与一次 authKey 消费。
- **我的驳**：边际覆盖低 ≠ 边际价值低。D-1 的义务是「register/**h2c**/derp 全部 exit 0」——**删掉阶段 3，regress 里就不存在 h2c 的 exit code**，D-1 字面变成不可满足（除非同时改 D-1 文本）。要保 D-1 不动而删阶段 3，唯一的诚实实现是把阶段 3 保留但让它有自己的 marker（=A）。因此「冗余」只否证了 A 的**收益**，否证不了 A 的**合法性**。反之 B 的成本不在代码，在**权限**：它要求代拍者行使改约权。
- **可代拍性**：**A 可代拍**（履约不触契约；判据充分、可机检）。**B 不可由本流程默认代拍**——若 owner 已于 2026-10-03 的授权中把 O2 整体授予，则 B 仍须满足三条件：①决策条目明写「本条**修订** TASK.md:54，删除 h2c 义务项」；②同步改 `TASK.md:54` 与 `docs/handover/agent-interop-regression.md:45-52` 验收段；③留 owner 追认位与重审触发（见 §7 模板）。
- **选错后果**：拍 B 而 owner 未授权 → 交接契约里出现「D-1 说要 h2c、regress 不跑 h2c」的**文本-实现背离**，正是 R14（未签署 DECISIONS 开工）同构的坑；真机 agent 到达 S2 时会按 D-1 去追问 h2c 证据，无处可取 → 剧本停摆。拍 A 的代价只是几十行 CLI，**不对称**。

### O3 headscale.device.yaml 红线豁免：豁免令的法定形式

- **选项**：A 签发**限域书面豁免**（仅设备侧、仅本任务、仅 LAN、用后即弃、到期自动失效）；B 不豁免，改用 ssh 端口转发/隧道让设备也走 127.0.0.1（技术上要求手机与 docker 同网络域，脚本成本高）；C 放宽原红线本身（禁 `0.0.0.0` 全局作废）；D 不动。
- **红线原文（我亲读到的三处，不依赖任何 thinking-*）**：
  ①`docs/handover/agent-interop-regression.md:54-62`「红线（不可放宽，违反即作废）」，其中 **:56「headscale 监听只绑 127.0.0.1；禁 `--network host`」**、:57「一切 HTTP 只对 `http://127.0.0.1:8080`」、:58 preauthkey 用后即弃、:61 私钥永不进 evidence/；②`TASK.md:88`「互操作只用隔离实例」；③`interop/regress.mjs:18-21` 脚本头注「仅在隔离 headscale 实例上跑（监听 127.0.0.1）」。
  **注**：PLAN/TESTS 里的「R1/R5」编号出自轨迹 4（我按禁令未读），我据仓内原文重建了红线条文——**这本身是一项不确定性**，但重建出的条文足以支撑本项判断。
- **一个必须先说的事实**：`interop/headscale.yaml:3` `listen_addr: 0.0.0.0:8080`、`:21` `stun_listen_addr: "0.0.0.0:3478"` ——**基线配置当前已经在违反上面这条红线**（TESTS V15 与 T-P1-9a 均已记，我亲读确认）。所以 P1-9 第 1 步（基线修回 127.0.0.1）不是豁免，是**红线归位**；O3 的豁免对象只能是**新建的设备侧文件**。
- **倾向 A**。推理链：设备与 headscale 不同机（PLAN D3/S6 前提），`server_url=127.0.0.1` 对手机等于连自己（死路），因此必须有一个例外面；例外只能是**新增文件 + 具名范围**，不能是「基线 yaml 继续用 0.0.0.0」（那等于红线从未被守住，且 C 选项会摧毁本仓唯一有实证价值的互操作红线）。
- **反方最强论证**：豁免令一旦签发，文本会被后续任务复制——「设备联调需要」这个理由在任何 LAN 场景都成立，于是红线事实上作废。这正是**先例漏洞**的机制：豁免的措辞比豁免的范围传播得快。
- **我的驳与解法**：漏洞不在「有没有豁免」，而在「豁免文本有没有可失效条件」。因此令文必须含**到期**与**撤销**两栏（本档 §7 给出模板草案），并写明**未被豁免的其余各条继续有效**（:57/:58/:61 逐条列举）。只要令文是「范围+时限+撤销+保留条款」四要素，先例就被封在文件里；反过来若只写一句「设备联调需要」，才是漏洞。
- **可代拍性**：**不可代拍（部分）**。豁免的**签发**是「对安全边界的例外」，属 owner 的职权；但**豁免文本的起草**、范围收窄、以及「基线归位」这一步（P1-9-1）可代做且应先做——先归位再谈例外，例外才显得是例外。
- **选错后果**：C（全局放宽）→ `agent-interop-regression.md:60`「不在远端执行任何改状态 tailscale CLI」等其余各条随之失效，隔离实例与宿主机共址风险回到本仓明确拒绝过的形态（`:56` 理由：避免与宿主机既有 tailnet 共址）。A 若写成无时限版本 → 真机窗口过去半年仍挂着 LAN 监听，撤销靠记性。

### O5 新增第 9 包：冻结的到底是什么

- **选项**：A 批准（承认「8 包」是叙述、冻结是导出面）；B 拒绝，kat 放 `packages/common/src/kat/`（消掉包计数变化）；C 批准但要求 owner 逐字改写 TASK.md:10 的冻结句。
- **证据**：①`TASK.md:10`「不推翻 8 包接口冻结（`docs/architecture.md` AU 清单是权威，续作**只增不改语义**）」——冻结句的宾语是「接口/语义」，主语才是「8 包」；②`docs/architecture.md:10`「本文是 `packages/` 下八个包的**实现契约**」；③`architecture.md:10.1`（:529-531）真正的冻结程序只写 common 的公开 API「只 import、不修改」，新增共享能力须「向架构师提修订…一次性合入」；④`architecture.md:551-552` v1.2/v1.3 记录：往既有包里**加文件**（controlbase.ts、tailcfg.ts、relay.ts、wgderive.ts…）是既有实践，未被当作破约。
- **倾向 A（并执行 C 的文本动作）**。推理链：冻结的可机检形态是**导出名集合只增不减**——TESTS §3.3-5 的 `frozen-exports.json`（396 名，我未跑 holdout，`node --test` 面 396 出自 TESTS V11）断言的正是 `当前 ⊇ 冻结`；包计数在这个断言里**不出现**。也就是说，「8 包」是一条文档叙述，不是可判定的约束。加第 9 包不触碰任何既有导出，故不违反冻结的**可判定内核**；它违反的是叙述，于是代价落在 P1-2 的口径工作上。
- **但冻结还有第二个内核，O5 也会碰它**：`architecture.md:1` 的包拓扑图 + D1/D2/D3 规则（:33-36）「derp 只许 import common」等。kat 必须 import 8 包来跑向量（PLAN P1-1：`runKat()` 是纯函数集，「零 node: 导入」≠ 零包导入），于是拓扑图多一个上游节点。这是**新增节点**不是**反向边**（8 包谁也不 import kat），D2 不被违反，但架构文档的图与「八包」措辞必须改。所以 O5 的正确姿态是：**批准 + 强制改两处措辞**（`architecture.md:10` 的「八个包」、`TASK.md:10`），而不是「知悉性拍板」什么都不做（PLAN O5 原文措辞偏轻）。
- **反方最强论证**：B 案（kat 塞进 `common/src/kat/`）零成本消掉包计数变化，且 common 本来就是「注入+常量+工具」的定位。反驳成本：kat 的向量来自 crypto/noise/wireguard/netcheck/derp/common **六个包**，塞进 common 会让 common 反向依赖它测试的那些包——D2 明确「common 不得 import 任何包」，虽然测试文件在 P3 范围外，但 `kat/run.ts` 是生产代码，**这会造出真实的反向边**。B 案技术上更脏。
- **可代拍性**：**可代拍**（事实可核、不需远端观测）。但由于它改的是 owner 的契约文本措辞，决策条目须写「本条不修改任何既有导出，仅修改两处叙述文本，且改后须过 T-A16-1 语境断言」。
- **选错后果**：若按 PLAN 原文「知悉性拍板」走过场 → 仓库里同时存在 9 个包和写「8 包」的活文档面，P1-3 文档门一开就红（README:10/:16、TASK.md:10、architecture.md:10、CONTEXT.md 均有），届时只有两条路：改门（掏空门）或改文档（承认没拍）。这正是 R8/P1-3 顺序锁要防的循环。

### R9 D4/P4 扩面 app/bridge/src：正当路径

- **证据（三层）**：①**现值 0 命中**：我用 CI 逐字等价式跑了 app/bridge/src（命令与输出见 §0 第 1–3 条，全空）；②**覆盖面缺口是结构性的**：根 `tsconfig.json` 的 `include: ["packages/**/*.ts"]` + `exclude: ["app"]`，而 `app/bridge/tsconfig.json` 是独立面 —— 即 `npm run typecheck`（A2）与 `npm run typecheck:bridge`（A3）**两张类型面**，D4/P4 门只覆盖了其中一张；③**纪律面的另一半没有门也没有目录**：PLAN §3.3「真机上网络 API 只允许出现在 `app/entry/src/main/ets/platform/`」，而我 `find app/entry/src -type f` 结果里**该目录不存在**（只有 3 个 .ets）。即这条禁则目前既无载体目录、也无机检。
- **倾向：采纳，但把「扩面」写成三件事而不是一件**：①把 P0-4 验收句改为**枚举检索面**（`packages/*/src` + `app/bridge/src`，逐项列明），门脚本头注释声明同一份面（R9 原文已有「显式声明检索面」的要求，我建议把它升级为验收句的强制项而非建议项）；②**明令 CI 与生产调用必须用默认根**（这条是我加的，见 R2）；③在决策条目里**记下 .ets 侧纪律面仍无机检**这一残余，不假装 R9 覆盖了它（真要覆盖需另开工作项：扫 `app/entry/src/main/ets` 的 `@ohos.net.*` 出现位置）。
- **正当路径的合法性论证**：扩面是**收紧**而非放宽。收紧从不需要「豁免权」，只需要「规格变更权」——而规格变更权在 owner，代拍流程已被授权处理 O 类与 R 类。R9 原文自己就说「属规格变更，走 owner 批准」，判断正确。相比 O3 的豁免，R9 是本批**最容易正当化**的一项。
- **反方最强论证**：扩面会引入误报成本。实测反例已现形：`app/bridge/src/mock-localapi.ts:229` 有 `const node: NotifyNodeView | undefined = ...`——裸 `node:` 字面量会被朴素写法误杀（我亲跑过，CI 的写法是 `from ['\"]node:` 才没中）。若 P0-4 门实现时把 pattern 写成裸 `node:`，门一落地就红，然后**修法通常是加豁免而不是修 pattern**——这正是 R13 要防的「全仓豁免也是绿的」。
- **我的驳**：所以 R9 与 R13 必须**同批拍、且把顺序写死**：先定「pattern 必须区分 import 形态与类型标注」（可用 `from ['\"]node:` + 显式 import/require/dynamic-import 三形态，T-P1-1b 已有三种形态的先例可抄），再谈任何豁免；每条豁免必须带非空 reason 并由 meta 断言（非空集、且不得是全集）。**先开门后定豁免 = 豁免自动生长**。
- **可代拍性**：**可代拍**。选错后果：pattern 写错 → 门假红 → 噪音 → 门被禁用（本仓 R12 已发生过同型：文档门先立后清导致噪音）。这是本项唯一的真实风险，且与「扩不扩面」无关——所以验收句必须把「误报面」也写成判据。

**关键设计点**：「未追认时的效力」这一栏把「代拍」的合法性从**授权推定**变成**默认分支**：默认分支必须选**不动约**的那一边（O2 默认补 CLI、O3 默认不豁免、R9 默认不扩面但记录缺口），这样即使 owner 永远不签，仓库也不会停在一个被单方面放宽的契约上。
