## 2. 轨迹叙事（图像如何被读取/批量处理、筛检判据、输出格式）

两轨共享同一套演化出的作业模式，轨2 在轨1 经验上明显升级了校验手段。

**阶段 A：整图初判 → 判定不可靠，退化为分块读取。**
两轨都先 Read 整张 contact sheet（轨1:L15、轨2:L13），随即都得出"太小无法可靠逐格判定"的结论（轨1:L84"联系表太小了…裁剪成放大的行条带"；轨2:L55"这张预览图太小"）。轨1 用 cv2 把 1500×1500 切成 10 条 3× 放大行条 `tmp_rows/row_00..09.jpg` 逐条 Read（轨1:L163-164、L86-99）；轨2 改切成 4 块 750×750 大 tile `crops/tile_r0c0..r1c1.jpg`（轨2:L60-61）。批量读取即"一次 Read 一条/一块"，靠格坐标（r行c列）保持记账。

**阶段 B：疑难格回源放大。**
对看不清的格子，用 Bash+cv2 从原图池裁出对应文件缩放到 ~640px 再 Read（轨1:L33、L108、L196；轨2:L96）。轨1 共对 24 个拿不准的格子回源复核（轨1:L161"对 24 个拿不准的格子…裁原图放大复核"）；轨2 复核了 42 张（轨2:L91"42 张不确定的图片已…高分辨率重新检查"），并把放大裁剪图留在 `out/b12_sheets/crops/check_*.jpg` 供审核。

**阶段 C：标签 OCR 校验——本族最核心的质量工序。**
contact sheet 每格标签是缩小的文件名文字，两轨都发生成批误读：
- 轨1 首次按误读名 imread 全部失败（轨1:L33-34 一串 `can't open/read file` WARN），由此意识到"imread 失败 = 标签读错"这一信号；先 `ls | grep -i "26186\|86e93"` 模糊定位（L36-37：`26186e93db`→实际 `28186e93db`），再把 100 个读出的标签写入 `/tmp/labels.txt` 与目录清单对账（L199-200），发现 7 个误读，用 `difflib` 模糊匹配逐一修正（L202-203，如 `49a7d98dd5→49a7a98dd5`、`d58d618195→a58d618195`）。最终总结称"发现并修正了 9 处缩略图标签误读"（L161）。
- 轨2 同样有 5 个标签在 `data/` 下 find 不到（轨2:L68-72），重放大格核对修正后仍不放心，进一步做了**内容级像素匹配**：把 100 个格图与 clean2 的 974 张原图做缩略图差分匹配（L80-81、L102-103）。首版匹配因 sheet 格内 letterboxing（留黑边）失败（L78），先分析格间边界结构（L105-106 检查 cols 130-170 的 BGR 均值确认白边/边界），改用 bounding-box 裁剪后重试成功（L103 输出每格最优匹配分）。共修正 7 个标签（`ace21cdf4d`、`2f711fdca4`、`b3cae8a142`、`cc92f668dd`、`bb6de773d8`、`268c697352`、`18c64e4494`，见 L91）。

**阶段 D：筛检判据的落地。**
- 轨1 的表"极不干净"：大量海南风景/地图/One Piece 罗（误抓"罗"字）同人图/书法"罗"字/商品包装海报/烘焙豆/拿铁/樱桃树果，真生豆仅 5 张（轨1:L161），KEEP_DEFECT 为空——"无一格符合缺陷豆标准"。
- 轨2 的表质量好得多，且留下了成文的边缘判例（轨2:L91）：字幕叠加的泡沫箱霉变绿豆 `5bba4f7303`→DEFECT；带虫孔的米色圆豆 `b5124ab96d`→DEFECT；哑光黑/发霉豆 `bec801738f`→DEFECT；手中日晒干豆 `cedf78d91e`→NORMAL；黄棕干豆带裂纹 `74ba6eab96`→NORMAL（裂纹≠烘焙裂开）；带标注的"虫蛀豆/正常豆"对比板（`c9377fa957`、`198d313d8f`、`a670a14123`）→DROP（一帧混类、半文档风格）；无法确认为咖啡的皱缩种子 `a6e1ad1a78`→DROP。这是"宁缺勿滥"策略的具体执行记录。

**阶段 E：输出与收尾。**
两轨最终都以纯文本三清单作答（轨1:L161：KEEP_NORMAL 5 项 + KEEP_DEFECT 空 + DROP 95 项；轨2:L91：26/6/68），并用 python 做终检：轨1 输出 `KEEP 5 DROP 95 TOTAL 100 missing-from-dir: [] dupes: 0`（轨1:L220-221），即清单与目录文件名、并/交/重条件全部满足；轨2 用 ls 计数确认 974 个源文件存在性（轨2:L108-109 逐名验证 `存在:1/不存在:0`）。轨1 还 `rm -rf` 清理了 tmp_rows/tmp_zoom（L220）。

## 3. 失败与恢复模式

| # | 失败 | 证据 | 恢复 | 评价 |
|---|---|---|---|---|
| F1 | 整图 Read 分辨率不足，无法逐格判定 | 轨1:L84、轨2:L55 | 切条/切块放大后分批 Read | 稳定的第一步退化策略，两轨独立复现 |
| F2 | cv2.imread 打不开文件（WARN）→ 源于标签 OCR 误读，文件根本不存在 | 轨1:L33-34、L169-170；轨2:L96-97 | 把 imread 失败当作误读探测器，触发 grep/find/difflib 校正 | 因祸得福：失败信号被转成质量闸门 |
| F3 | 对 imread 返回 None 的图直接 cv2.resize → `(-215:Assertion failed) !ssize.empty()` 崩溃 | 轨1:L69-70、L140-141；轨2:L57-58 | 轨1 引入 `imread_u = imdecode(np.fromfile(p))`（兼防中文路径）+ 存在性检查后重跑 `ok` | 同一坑两轨各踩 1-2 次，属可回归复现的确定型错误 |
| F4 | 临时放大图批次间互相覆盖 | 轨1:L117"第一批缩放文件被第二批覆盖了" | 改用 z/y 两套前缀分批命名 | 并行批次写同一目录的命名卫生问题 |
| F5 | Read 尚未生成/已被覆盖的文件报 error | 轨1:L39-40（z02…7538464339）、L232-233（z07…28186e93db） | 重新生成（L241 z12）后重读 | 生成-读取竞态，靠重试消化 |
| F6 | 验证裁剪列坐标差一（off-by-one） | 轨1:L149"我的验证裁剪存在'差一'错误" | 用正确列索引重裁 7 格 | 网格坐标换算是高频出错点 |
| F7 | 像素匹配因格内 letterboxing 失败 | 轨2:L78 | 先做边界/留白分析（L105-106）再 bbox 裁剪重试（L103） | 结构先验 → 算法适配的良好范例 |
| F8 | numpy hstack 拼接合成图报错 | 轨2:L99-100 | 重写拼接逻辑继续 | 一次性脚本脆性 |
| F9 | 标签在目录中完全 find 不到（5 个） | 轨2:L68-72（全空输出） | 重放大该五格 + 全量像素匹配兜底 | 从"信标签"升级到"信内容"，轨2 独有的系统化兜底 |
| F10 | 全程未用 TodoWrite，收到 3+2 次系统提醒 | 轨1:L9/L11/L13、轨2:L9/L11 | 未响应 | 单一长流程任务中任务列表被忽略；对结果无影响但流程可见性差 |

共性问题：cv2 脚本一次性 `-c` 内联、无空值防护（F3 反复出现）；标签这个小字号 OCR 是全族最大噪声源（两轨合计 16 处误读修正，均被目录对账拦下）。

## 4. 可复用资产线索

1. **case-id 建议：`beaneye-sheet-triage-100`**（视觉筛检 bench 主用例）
   - 输入：1500×1500、10×10、150px/格、带文件名标签的 contact sheet + 三分类判据提示词（可直接复用轨1:L7/轨2:L7 的提示词模板，含"拿不准就 DROP"）。
   - 预期：100 格每格恰归一类，输出三清单；参考真值：轨1 为 5/0/95（KEEP_NORMAL=normal_d32f333f30, e653a907d2, 93c5e2bc0f, 8d0d032897, 9cb58288e1，轨1:L161/L221），轨2 为 26/6/68（KEEP_DEFECT= n2_5bba4f7303, b5124ab96d, dae89e48e1, e02fb5146e, 7ec35815c0, bec801738f，轨2:L91）。
   - 判分：逐格三分类准确率（主指标）+ KEEP 类查准/查远（宁缺勿滥 → 侧重 KEEP 精度）；附完整性硬校验：三清单并集=100、两两不交、无 .jpg 后缀、无重复。
   - 难度：hard（细粒度视觉判别 + 标签 OCR + 100 项记账）。
2. **case-id 建议：`beaneye-label-ocr-vs-dir`**（标签误读回归）
   - 输入：故意混入易混标签的 sheet（真值对：7538464539↔7538464339、26186e93db↔28186e93db、c00f7d0f27↔c00f7a0f27、d58d618195↔a58d618195，取自轨1:L103-104/L202-203；ace21cf44d↔ace21cdf4d 等，取自轨2:L108-109）。
   - 预期：agent 将全部输出文件名与源目录对账（轨1 做法：/tmp/labels.txt + 全量比对 L199-200），不存在的名字经 difflib/grep 修正到真实文件。
   - 判分：最终输出中"不存在于源目录的文件名"数必须为 0（轨1 终检即打印 `missing-from-dir: []`，L221）；再加误读召回率。
   - 难度：medium。
3. **case-id 建议：`cv2-none-guard-regression`**（图像读取回归）
   - 输入：Bash+python 内联 cv2 脚本，要求裁剪/缩放一组路径，其中若干路径不存在（或含中文/非常规字符）。
   - 预期：不因 `imread→None→cv2.resize` 抛 `!ssize.empty()` 崩溃（复现轨1:L70/L141、轨2:L58）；正确形态是先判存在性、或用 `cv2.imdecode(np.fromfile(p,...))`（轨1:L140/L208 的 imread_u 助手）。
   - 判分：脚本 exit 0、对缺失项给出显式 MISSING 列表、其余裁剪产物落盘且可 Read。
   - 难度：easy。
4. **case-id 建议：`beaneye-tri-list-format-check`**（输出格式校验用例）
   - 输入：筛检任务的原始输出文本（含括号逗号列表形态，如轨1:L161）。
   - 预期：可解析出三个段 `KEEP_NORMAL/KEEP_DEFECT/DROP`，项为不带 .jpg 的裸文件名；并集恰 100、无重复、无交叉。
   - 判分：程序化正则抽取 + 集合断言，输出 `TOTAL 100 / dupes 0 / missing 0` 风格报告（直接仿轨1:L220-221 的终检脚本）。
   - 难度：easy。
5. **case-id 建议：`beaneye-cell-pixel-match`**（sheet 格↔原图内容匹配）
   - 输入：contact sheet + 974 张原图目录（轨2 场景），格内图有 letterbox 留边。
   - 预期：先探边界（轨2:L105-106）再做 bbox 裁剪 + 缩略图差分，输出每格→源文件映射及分数（轨2:L103），冲突格单独复核。
   - 判分：映射准确率（对已知真值映射）；letterbox 未处理时首版必败（轨2:L78 可作负例断言）。
   - 难度：hard。
6. **case-id 建议：`beaneye-edgecase-policy`**（边缘判例一致性）
   - 输入：轨2:L91 记录的 8 个成文判例（霉变+字幕→DEFECT；虫孔→DEFECT；哑光黑霉→DEFECT；手中日晒干豆→NORMAL；黄棕干豆带裂纹→NORMAL；标注对比板×3→DROP；不可确认种子→DROP）。
   - 预期：不同 run 对同一批边缘图给出一致归类，维持"宁缺勿滥"。
   - 判分：与上述判例真值的逐项一致率；DROP 类允许向 KEEP 误升零容忍。
   - 难度：medium。
7. **case-id 建议：`tmp-crop-hygiene`**（临时文件命名与清理）
   - 输入：需多批次生成放大裁剪图到同一 tmp 目录的长流程。
   - 预期：批次用可区分前缀（轨1 z/y，L117 教训），结束清理 tmp 目录（轨1:L220 `rm -rf`）。
   - 判分：中途无"文件被覆盖后再被读"的 error Read（轨1:L39、L232 为反例）；结束时 tmp 目录不存在。
   - 难度：easy。

## 5. 数据质量备注

- **导出乱序**：两份 txt 中 TEXT 与 TOOL 块非严格按时间排列——轨1 的最终答复（L161，13:45）出现在大量 13:34-13:44 的工具调用之前/之后交错；重建叙事必须按 @时间戳与逻辑依赖重排，不能按行序读。
- **工具输出截断**：两轨的最终 DROP 清单均被 `…[截断]`（轨1:L161、轨2:L91），完整 95/68 项清单无法从日志恢复；多数 Bash 命令体也被截断，只能靠 out: 片段推断脚本内容。
- **图像内容不可审计**：所有 Read 图片的 out 均为 `[Attached image/jpeg: Read image]`（轨1:L16 等），日志中不含像素；agent 对格子内容的描述（如"泡沫箱霉变绿豆"）只能作为声明采信，无法从轨迹复核视觉判断本身。
- **文本污染**：系统提醒（TodoWrite 提示）被记为 TEXT 条目（轨1:L9/L11/L13），并非用户输入；轨2:L97 的 cv2 WARN 中出现字面 `\n`（`clean2\n2_2f711fdc04.jpg`），说明命令字符串内嵌了换行转义，属导出或原始命令的转义伪影。
- **计数口径**：轨1 自述"9 处误读"（L161）但对账明细仅列出 7 个（L138/L202-203），2 处差额无从对证；parts 数（193/121）与日志可见条目数不一致（导出有压缩）。时间戳仅分钟精度。
- **判值可信度**：两轨的最终清单均通过"目录存在性 + 100 无缺无重"硬校验（轨1:L221、轨2:L108-109），文件名层面高可信；类别层面（NORMAL/DEFECT/DROP 是否判对）无 ground truth 旁证，仅轨2 留有 crops/check_*.jpg 复核材料（轨2:L91）可作事后审计入口。
